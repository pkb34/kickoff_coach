# WPTI: World Football Personality Type Indicator

This is a three-page, Python-only Streamlit prototype. Question selection and data processing run locally. The result page has an optional Gemini briefing requested by the student. In this v8 copy, the welcome page keeps the original still illustration. Its native aspect ratio keeps every football player's body in view. A direct video-model attempt was blocked by the configured Gemini key's free-tier limit; see `../VIDEO_MODEL_TRIAL.md`.

## Current flow

1. **Welcome:** the original illustrated international football match, shown in full without cropping players or adding role labels, then **Discover My WPTI**. Page entry has a small slide-in effect. There is no one-week-test claim or unnecessary assessment disclaimer.
2. **Quiz:** three starting question groups cover activity type and typical weekly activity hours, class hours, weekday and weekend study hours, and usual nightly sleep. Each time question has seven selectable ranges plus **Not sure** and **Skip**. Common values have smaller ranges; uncommon high or low values have broader ranges. The buttons fit in short rows without horizontal scrolling. The original rounded Fredoka font is restored for headings and answer buttons. The local question agent asks seven deeper questions and at most one conditional question. The academic-progress question has its own artwork, and an unfamiliar question ID uses fallback artwork instead of crashing the page. Earlier conversation is collapsed. After the last answer the app saves and goes directly to results.
3. **Result:** local analysis keeps reported time intervals as intervals and calculates approximate weekly intervals from weekday and weekend study ranges. Midpoints are available for internal compatibility but are never displayed as exact student reports. The page also shows a student's own academic-progress choice and scales their direct feeling rating to 0–100. Four contextual answers estimate one of 16 WPTI letter types, each mapped to one of eight evenly distributed football positions. Skipped or unrecognized answers leave the type unassigned rather than inventing traits. Eight distinct characters with different role actions share one sprite sheet. The left character has subtle 2D motion, while the right-hand description uses reported time ranges and the academic-progress answer. Official VT links are selected based on activity type and relevant self-reported needs. Students can optionally request an empathetic Gemini briefing with two practical tips and a possible future-moments paragraph. Numerical future predictions are not implemented.

An optional sound toggle offers a newly composed, bright major-key loop with marimba, soft ukulele, flute, and a quiet shaker, plus gentle button cues. It plays through a hidden audio element, without a media-control bar. If the browser blocks autoplay, a small **Tap to start the little tune** button appears. Completing the quiz shows confetti and attempts to play a short original stadium-style cheer; that cheer has a small replay button instead of a media bar. The audio is original and is not based on a World Cup theme song. Music restarts when Streamlit changes pages.

The active question agent is `local_question_agent.py`. It uses transparent Python rules to choose questions from a local bank based on the student's answers. It is **not** a locally hosted language model and does not generate arbitrary new prose. `wpti_types.py` maps answers to four estimated axes, 16 codes, and eight positions; these are playful preferences, not validated psychometric scores. The quiz and result pages are `views/quiz.py` and `views/result.py`. Voice input appears only for open-ended follow-up questions. It uses browser speech to read the question and `st.audio_input` plus the configured Gemini key to interpret one recorded answer at a time. The recording is sent to Gemini after the student presses **Send my voice answer** and is not stored in SQLite. Text answers remain local. This is turn-by-turn voice input, not a continuous live generative conversation.

The local analysis is `analysis_agent.py`. Its happiness index is **only the student's own 0–10 answer multiplied by ten**; it is not a validated wellbeing scale. `football_matches.py` holds editable national-team analogies and links to football sources. `gemini_gateway.py` handles the optional student Gemini request. It sends selected time ranges with their approximate midpoints, the self-rating, and answer-availability flags. Gemini is instructed to describe the ranges rather than claim exact hours. It does **not** send names, activity descriptions, free-text replies, or the transcript. When Databricks is configured, a click on **Make my gentle game plan** also adds the approved synthetic telemetry fields—study hours, extracurricular count, credit hours, and assignment-start style—to that Gemini request. Synthetic telemetry is separate demo context and must not be treated as this student's data. Gemini text is shown as a possible scenario, not a forecast.

**Current scope rule:** the quiz must never ask about academic marks or grade point average. The active baseline schema does not contain that field. The older `collector.py`, `collection_gateway.py`, and `followups.py` are legacy code retained for old records/tests; they are not imported by the active quiz. Do not reconnect them to the quiz.

## Run locally

From this directory in PowerShell:

```powershell
py -3.14 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m streamlit run app.py --server.address 127.0.0.1 --server.port 8512 --browser.gatherUsageStats false
```

Open <http://127.0.0.1:8512/> for the v8 preview. To run the tests:

```powershell
.\.venv\Scripts\python.exe -m unittest -v
```

Confirmed records and conversation transcripts are stored locally in `data/submissions.sqlite3`; set `STUDENT_DB_PATH` to choose another database. New completed check-ins enter a durable local sync queue. When Databricks is configured, the app uploads the structured record and result to a separate Delta table; it does **not** upload the conversation transcript or voice recording. If the connection is unavailable, the check-in remains locally saved and queued for retry. Students should avoid entering names or other identifying information. The app has no validated performance or wellbeing prediction.

## Staff overview

The staff page is a **separate local app**. A small **Staff access** link at the bottom of the welcome page opens it. In PowerShell, from this folder run `./run_staff.ps1`, create a password when prompted, then open <http://127.0.0.1:8513/> or use the homepage link and enter that password. The password is kept only in the process environment for that run. The dashboard charts use horizontal labels. Authenticated staff can see the count of locally queued Databricks writes and retry them after configuration. The page shows aggregate counts of self-reported academic progress, feeling ratings, and football roles. It does not show names, transcripts, or individual answers. With at least ten completed check-ins and a configured Gemini key, authenticated staff can click **Generate group report with Gemini**. A checked table displays the answer count and group estimate for each measure. `staff_report.py` sends only aggregate counts, approximate averages, and rounded percentages to Gemini, then displays its qualitative overview, wellbeing and academic-progress paragraphs, support ideas, and limitations. Gemini prose may not repeat numbers; staff should use the checked table for exact figures. A measure with fewer than five answers has its numerical results suppressed in the Gemini request. No individual record, transcript, free-text answer, or student identifier is sent. The report is descriptive; a genuine prediction model would require validated historical outcomes and evaluation.

## Optional Gemini connection

This workstation has a private `.streamlit/secrets.toml` with `GEMINI_API_KEY` and `GEMINI_MODEL`. The file is ignored by Git and must not be committed. On another machine, copy `.streamlit/secrets.toml.example` to `.streamlit/secrets.toml` and fill in a key, or set the `GEMINI_API_KEY` environment variable. The default model is `gemini-2.5-flash-lite`; change `GEMINI_MODEL` only if your API key has access to another Gemini text model. The API is called only after a student clicks **Make my gentle game plan** or authenticated staff clicks **Generate group report with Gemini**. If a request fails, the local charts and analysis remain available.

## Optional Databricks personalization

Put the four `DATABRICKS_...` values from `.streamlit/secrets.toml.example` in your ignored local `.streamlit/secrets.toml`. Set `DATABRICKS_DEMO_STUDENT_ID` to one synthetic `student_id` in `main.pitchside.student_checkins`, such as `VT-DEMO-001`. When both Databricks and Gemini are configured, the app fetches that synthetic record only when the student clicks **Make my gentle game plan**. It sends Gemini only study hours, extracurricular count, credit hours, and assignment-start style—never the student ID, token, raw table text, or quiz transcript.

## Databricks storage for completed check-ins

The app's new write path needs `DATABRICKS_SERVER_HOSTNAME` and `DATABRICKS_HTTP_PATH` in ignored `.streamlit/secrets.toml` or environment variables. In Databricks, open **SQL Warehouses**, select a running warehouse, and copy its **Server Hostname** and **HTTP Path** from **Connection details**. For a local demo with browser sign-in, set `DATABRICKS_AUTH_TYPE = "databricks-oauth"`; authenticated staff should run the first sync and complete sign-in before students use the quiz. For unattended hosting, use an appropriately scoped noninteractive credential instead; this prototype also accepts `DATABRICKS_TOKEN` with the default `pat` mode. The signed-in identity and warehouse must have permission to create and write a Delta table in the chosen catalog and schema. Never put a token in source code or GitHub.

The default target is `main.pitchside.wpti_submissions`, separate from synthetic `main.pitchside.student_checkins`. Set `DATABRICKS_SUBMISSIONS_TABLE = "catalog.schema.table"` to choose another location. The server creates the schema and table if allowed, then uses a parameterized, ID-based Delta `MERGE` so retries do not duplicate a check-in. The cloud rows contain `submission_id`, `created_at`, `record_json`, `result_json`, and `synced_at`. The structured record can contain a student's free-text answers; audio and the full conversation transcript stay local. The staff dashboard remains based on local SQLite aggregates. Existing check-ins from before this feature are **not** uploaded automatically; authenticated staff can explicitly queue them in the dashboard.

If Databricks is not configured or a write fails, new check-ins remain queued in local SQLite. The next completed check-in retries a batch, or authenticated staff can press **Sync pending check-ins to Databricks**. Verify a row from the Databricks SQL editor with `SELECT submission_id, created_at FROM main.pitchside.wpti_submissions ORDER BY created_at DESC LIMIT 5`. Do not commit the local SQLite database; real student responses need consent, access controls, and a retention/deletion policy before production use.
